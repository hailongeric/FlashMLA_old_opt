## Algorithm and interface

`flash_mla_interface.py` selects a backend using the input tensor's device, not
the process's current CUDA device. Capability 9.0 uses the lazily imported native
Hopper extension; capability 12.0 uses `sm120.py`; other devices fail explicitly.

The RTX attention kernel tiles 16 grouped query rows and 32 KV tokens, splitting
the 576 Q/K channels into 512 non-positional channels and 64 additional channels.
It loads keys through the page table. The first 512 key channels also provide
the values. Tensor-core matrix products use FP16/BF16 operands with FP32
accumulation. Online softmax avoids materializing the full attention matrix.
Probabilities are rounded to the input dtype for the value matrix product.

The split count is bounded by cache capacity, a maximum of 32, and an occupancy
heuristic using the GPU's actual SM count. Each request divides its live length
into approximately equal 32-token-aligned splits. For multiple splits, each split writes a normalized FP32 output and a base-2
LSE to global scratch. The merge kernel weights these outputs by their stable
exponential weights and converts final LSE to the natural-log convention.
The optimized path writes final output directly for a single split with table
capacity at most 256 tokens. Longer single-split requests retain the FP32
attention epilogue and use a dedicated copy/conversion kernel. See the reduction
report for the measured launch policy.

This path uses ordinary GPU memory for partials. It does not use the original
Hopper scheduler, WGMMA, DSM, or cluster TMA exchange. The separation avoids
pretending that a change to an architecture guard makes `sm_90a` code portable.
NVIDIA documents this limitation in its
[Blackwell compatibility guide](https://docs.nvidia.com/cuda/blackwell-compatibility-guide/index.html).

Supported inputs:

- FP16 or BF16 Q and cache tensors, Q/K dimension 576, value dimension 512.
- 64-token pages with shared K/V storage and any positive KV head count dividing
  the query head count.
- Variable cache lengths, nonsequential page tables, multiple query tokens,
  and noncontiguous outer strides with contiguous channel dimensions.
- Optional finite softmax scale, including zero or negative values.
- Bottom-right causal masking: `key_pos <= cache_len - seq_q + query_pos`.
- Empty sequences and fully masked rows, returning zero output and `-inf` LSE.
- CUDA graph replay with in-place length changes, within the allocated table
  capacity. Warm the relevant shape/dtype specialization before capture.

Lengths must be contiguous CUDA int32 with shape `(batch,)`. The table must be
CUDA int32 with shape `(batch, max_pages)` and contiguous columns. Live lengths
must be between zero and `64 * max_pages`; each live page ID must index the
cache. Python checks tensor shapes, dtypes, device consistency and scale. It does
not synchronize the GPU to validate every table element or length value. Kernel
bounds masks are defensive; malformed cache contents are not supported inputs.

Both scheduling results remain tensors, but they are opaque backend state.
SM120 returns shapes `(0, 8)` and `(0,)` as markers; lengths are read directly by
the kernel. Hopper retains its original metadata tensors. Recreate metadata when
changing backends/devices, and never interpret the RTX markers as a Hopper split
prefix sum. No backward pass, FP8, separate value cache, or general head-dimension
support is implemented.

## Local environment and headers

From the repository, source `scripts/rtx6000d_env.sh`. It activates the requested
environment, sets project-local caches and temporary directories, and adds local
Python headers to `CPATH` when present. It changes only the invoking shell's
environment; no shell profile or global package configuration is modified.

The server initially lacked `Python.h`, which Triton needs to compile its Python
launcher. The matching Ubuntu development package was **downloaded and extracted**
under the project, without installing it through apt:

```text
~/nhl_project/toolchains/downloads/python3.12-headers/
  libpython3.12-dev_3.12.3-1ubuntu0.17_amd64.deb
~/nhl_project/toolchains/python3.12-headers/
```

Archive SHA256:
`c123ddab7763e45199e21b4ac8545e705f20a0315b9ada4c236b52fb088c4e16`.
Its version matched the installed system Python package. The downloaded package
came from the machine's configured Ubuntu mirror. No system apt installation,
index update, conda environment, or global pip change was performed.

For this Ubuntu/Python 3.12 setup, if recreating the missing local headers:

```bash
mkdir -p ~/nhl_project/toolchains/downloads/python3.12-headers
cd ~/nhl_project/toolchains/downloads/python3.12-headers
version=$(dpkg-query -W -f='${Version}' python3.12)
apt-get download "libpython3.12-dev=${version}"
dpkg-deb --extract "libpython3.12-dev_${version}_amd64.deb" \
  ~/nhl_project/toolchains/python3.12-headers
cd ~/nhl_project/moore_tma_pj/kernels/FlashMLA_old_opt
source scripts/rtx6000d_env.sh
```

The exact matching package must still be available in the configured repository.
Do not replace these commands with a global installation on the shared account.

## Initial-port validation (historical)

At initial-port revision `1f168a52a4bce6d34439991ee63070d6a0c49825`,
`tests/test_sm120.py` contained five test methods. The current suite contains
seven; see [the reduction report](RTX6000D_REDUCE_BENCHMARK.md#correctness-and-preservation).
The initial numerical method exercised
10 configurations in both BF16 and FP16 (20 comparisons), including cache lengths
0, 1, 2, 17, 63, 64, 65, 129, 257, 511, 1025, 4097 and 32768. Batch sizes range
from 1 to 4, query lengths from 1 to 4, query heads from 1 to 128, and KV heads
from 1 to 3. Page tables are shuffled; padding is poisoned with NaNs or invalid
page IDs to expose accidental padding reads. One case uses padded outer strides.

The independent reference gathers paged K/V and computes attention in FP32,
with TF32 disabled. Output checks combine elementwise tolerances and a normalized
squared-error threshold below `1e-5`. LSE is checked independently with
`atol=2e-4, rtol=2e-5`. Graph replay is checked at original, shorter/empty, and
restored lengths. Input errors and CPU/unsupported-device rejection are checked.
Hopper dispatch is checked with a mocked extension; it is not an H100 GPU test.

All five methods passed, with no skipped tests. There were 24 reference
comparisons including graph checks and the benchmark precheck. The maximum
observed absolute output error was approximately **0.00804**, and the maximum
normalized squared error was **2.23e-6**. The absolute tolerance combines with the
relative tolerance; the maximum error alone is not the pass criterion.

The recorded run is in [RTX6000D_VALIDATION.json](RTX6000D_VALIDATION.json), with
the tested source hashes and individual case metrics. Server logs, package
inventories, header provenance and file backups are retained at:

```text
~/nhl_project/moore_tma_pj/docs/rtx6000d_adaptation_20261023/
```

No H100 was available on this server. Hash verification covers all 11 tracked
CUDA source files outside the CUTLASS submodule against the pre-port state; the
submodule and native kernel code were not changed. The original H100 experimental
correctness and synchronization questions remain documented in
[TMA_REDUCTION.md](TMA_REDUCTION.md).

## Initial-port timing and next work

For batch 1, one query token, 128 query heads, one KV head, 32768 KV tokens,
BF16 and causal mode, 100 warmed repetitions gave:

| Boundary | Mean time |
|---|---:|
| Eager forward, both kernels including launch/allocation gaps | 0.17084 ms |
| CUDA graph replay, both kernels with captured allocations | 0.17143 ms |

These CUDA-event measurements exclude metadata creation, JIT compilation,
reference attention and host-to-device transfers. They are one short run on a
shared machine, not a throughput study or a claimed improvement over H100 or
another library. GPU clocks, concurrency and cache state can change the result.

Useful next steps are broader production-shape validation, controlled baseline
measurements on the same GPU, tuning query/KV tiles and split counts, and reducing
global intermediate traffic. Keep this working SM120 path as a correctness
baseline when investigating a more specialized Blackwell reduction. Continue
H100 DSM work separately on hardware that can execute and validate it.
